# 云裳 AI 导购 · 零售场景 AI 助手 Demo

>  在线体验：https://www.coze.cn/store/agent/7698274383365816360?bot_id=true

>
> 从零搭起来的一个服装零售 AI 导购 Demo。零代码，扣子平台。
> 目的不是炫技，是验证一个问题：**怎么让大模型推荐的商品是真的、不编造、说得清理由。**

---

## 一、要解决的问题

传统电商搜索只会关键词匹配。顾客说：

> "想找 300 以内、能送同事、上班也能穿的裙子"

系统拆出"300""裙子"，返回一堆不相关结果。真人导购会先理解**场景（送礼）、用途（通勤）、预算**，再筛选。

大模型能懂人话，但它有个致命缺陷：**会编造不存在的商品、价格和库存**。零售场景下，这是商业事故。

所以本项目的核心命题是：

> **如何让大模型既听得懂人话，又只推荐真实存在的商品？**

答案：**用结构化商品数据（简化版知识图谱）做大模型的"事实底座"，再加强制检索。**

---

## 二、架构设计

```
用户输入
   ↓
① 意图理解（LLM）—— 从口语中提取结构化条件
    品类 / 颜色 / 风格 / 场景 / 预算 / 材质偏好
   ↓
② 知识库检索（结构化查询，非 LLM）—— 按条件召回候选商品
    ← 商品知识库（50 SKU，13 个字段）
   ↓
③ 推荐生成（LLM）—— 只能使用召回结果，禁止编造
    商品名 + 价格 + 卖点 + 适用场景
   ↓
④ 兜底逻辑
    召回为空 → 诚实说没货，推荐近似款，绝不虚构
    需求模糊 → 反问 1-2 个问题澄清，不连环追问
```

### 设计取舍

| 环节 | 方式 | 为什么 |
|------|------|--------|
| 意图理解 | 大模型 | 输入是自然语言，规则无法穷举 |
| 商品检索 | **结构化查询，不用大模型** | 要毫秒响应、结果确定、可审计 |
| 推荐生成 | 大模型 | 组织语言、解释理由，这是它的强项 |
| 兜底/红线 | 固定规则 | 商业红线不能交给模型自由发挥 |

一句话：**能用规则和结构化查询解决的，绝不交给大模型；只有"理解语言"和"组织表达"两件事才用 AI。**

## 三、数据设计（微型知识图谱）

50 个 SKU，13 个字段。重点不在字段多少，而在**字段之间的关系**。

| 字段 | 类型 | 设计说明 |
|------|------|----------|
| 商品ID | 实体主键 | P001 ~ P050 |
| 商品名称 | 实体属性 | 推荐时展示 |
| 品类 | 分类属性 | 连衣裙 / T恤 / 衬衫 / 半身裙 / 裤装 / 外套 / 针织衫 / 套装 |
| 颜色 / 色系 | 属性 | "深色系"可作为抽象查询维度 |
| 材质成分 | 属性 | 如「棉95% 氨纶5%」 |
| **弹性** | **推导属性** | 由材质自动推导：**氨纶 ≥ 3% → 有弹性**。这是「实体 + 关系」的典型例子——机器记的不是词，是推理规则 |
| 风格 | 属性 | 法式 / 通勤 / 甜美 / 复古 / 韩系 / 运动风 |
| **适用场景** | **关系** | 多值字段（通勤、约会、送礼、宴会…），连接「用户需求」与「商品」的关键边 |
| 价格 | 属性 | 预算过滤 |
| 季节 | 属性 | 季节性推荐 |
| 库存 | 属性 | 缺货判断 → 触发近似推荐 |
| 卖点标签 | 属性 | 生成推荐理由的素材 |

**为什么管这个叫"知识图谱"？**

真实的知识图谱是**实体 + 关系 + 推理规则**。本 Demo 用表格模拟了最小版本：

- 实体：商品
- 关系：商品 → 场景、商品 → 风格
- 推理规则：成分含氨纶 → 有弹性；场景含"上班" → 归入通勤需求

> 这也是为什么"只靠大模型"不够：大模型知道"氨纶有弹性"，但它不知道**你店里哪件衣服含氨纶、库存几件、卖多少钱**。事实必须在图谱里。

## 四、版本迭代全记录

这个 Demo 从 v1 到 v5 一共迭代了五轮，每一轮都是被一次具体的问题逼出来的。下面按时间顺序记录，**包括所有失败和翻车**。

### 版本总览

| 版本 | 触发问题 | 做了什么 | 结果 |
|------|----------|----------|------|
| **v1 基础版** | —— | 建 50 SKU 知识库（13 字段）+ 简单角色提示词 + 推荐规则 | 能跑，但推荐单薄、不会追问 |
| **v2 主动澄清版** | 输出只有 1 款商品，不让顾客选 | 加【推荐数量 2-4 款】+【主动澄清】+【尺度控制】+【术语翻译】 | 会追问了，但触发不稳定 |
| **v2.1 强制澄清** | "想买上衣"没有主动问，直接推了 2 款 | 把"或先展示 2-3 款"删除，改成必须反问 | 稳定先问再推 ✅ |
| **v3 暴雷版** | 输出 3 件商品，**全部是编造的** | 开始排查 | 发现检索召回为空 |
| **v4 修复版** | —— | min_score 0.5→0.3、混合检索、强制检索条款、温度降至 0.1-0.3 | 不再编造 ✅ |
| **v5 术语可读版** | "有弹性/微弹"顾客分不清 | 加术语翻译层，数据层保留专业字段，展示层翻译成体感语言 | 推荐话术更自然 ✅ |

---

### v1：先让东西跑起来

**做法**：把 50 个 SKU 传成表格型知识库，写一段最朴素的提示词（"你是导购，根据知识库推荐商品，不要编造"），挂上知识库直接测。

**问题**：
- 顾客说"300 以内送同事的裙子"，它只推 1 款
- 顾客说"想买上衣"，它劈头盖脸推了 2 款，不问偏好

**当时的诊断**：提示词没有规定推荐数量和追问规则，模型按"最省事"的方式回答。

---

### v2：加"主动澄清"，但没写死

**改动**：

```
【主动澄清】需求模糊时，用一句话给选项让顾客选，例如：
   - 顾客说"上衣" → 主动问"想要T恤、衬衫还是针织衫？"
每次最多问1-2个问题
```

同时在"尺度"里写了一句：*需求模糊 → 先问1个问题，**或先展示2-3款**探探偏好*。

**为什么加这句**：怕模型太机械，想给它一点灵活空间。

**结果**：埋雷了。模型选了省事的那条——推 2 款 + 结尾顺带问一句，而不是先问。

```
法式泡泡袖上衣 299 元…
法式泡泡袖衬衫 699 元…
要不要我给你发这两款的细节图？要是你想要T恤、针织衫类的也可以告诉我
```

**教训**：**提示词里出现"或"字，模型永远选工作量小的那个分支。** 想要确定行为，就不能给选项。

---

### v2.1：把"或"删掉

**改动**：删掉"或先展示2-3款"，改成强制语气：

```
【主动澄清·强制】当顾客只说了宽泛品类（"上衣""下装""裙子"），
而没给场景或预算时，必须先反问再推荐。
只有当顾客已给出场景/预算/风格中至少一项时，才可以直接推荐。
```

**结果**：输入"想买上衣" →

> 想要哪种呀？半身裙有复古、法式、甜美等多种风格，告诉我场合或预算，我帮你挑得更准～

✅ 稳定先问了。

**顺带发现**：这轮回复暴露了另一个隐患——它推的第二款"法式泡泡袖衬衫（黑色）699 元"，颜色价格都要回表核对。真商品 + 假属性，比完全编造更隐蔽。

---

### v3：翻车。模型凭空造了三件裙子

**测试输入**："300 以内送同事的裙子"

**输出**：

- 碎花茶歇半身裙 159 元
- 藏青A字西装裙 229 元
- 冰丝针织连衣裙 279 元

**全是假的。** 铁证：

- 商品表里价格只可能是 129/149/169/199/239/259/299/329/399/459/499/599/699/899/1099，**159/229/279 根本不在集合内**
- 商品名是把表里真实的"茶歇法式长裙""高腰A字半身裙"揉捏拼接出来的

**排查（关键一步）**：不要猜，去看调试详情。

扣子右侧有"调试详情 → 调用树"，展开看：

```
├─ 用户输入
├─ 知识库 Knowledge      ← 检索确实执行了
├─ 调用 LLM 豆包 2.0 pro
└─ 调用 LLM Seed Suggest

知识库节点输出：
{ "slices": NULL }
```

左侧运行过程也写着：**"没有召回相关的切片 2.8s"**。

**结论：不是模型无视了检索结果，而是检索一条都没召回到，模型拿不到事实，只能自己编。**

**这一步的意义**：区分"模型不听话"和"数据没喂进去"——两者的修法完全不同。很多人会先去改提示词，但真正的问题在召回层。

---

### v4：修召回，不是修模型

**根因**：最小匹配度（min_score）默认 0.5。"300 以内送同事的裙子"这句口语，和商品行的字面重合度很低，全被 0.5 这条线拦死。

**改动清单**：

| 项 | 改动 | 理由 |
|----|------|------|
| 最小匹配度 | 0.50 → **0.25** | 让召回有货，是第一优先级 |
| 搜索策略 | 语义 → **混合**（语义+全文） | 型号、材质这类精确词需要全文兜底 |
| 查询改写 | 开启 | 把口语改写成检索词 |
| 提示词 | 加"强制检索"最高优先级条款 | 双保险 |

**验证**：输入"300 以内送同事的裙子"，调用树里的知识库节点**不再为空**，输出商品与表内数据逐条对得上。

**教训**：
1. **RAG 系统的第一故障点永远是召回，不是生成。** 召回为空时，再好的提示词也救不了。
2. **排查顺序应该是：看调用树 → 看召回结果 → 再看模型输出。** 顺序反了会浪费大量时间改提示词。

---

### 事故 2（贯穿多版本）：模型"自查"是自欺

漏出的思维链里，模型反复写：

> "哦对哦，检查有没有违反红线？没有，都是合理的，对吧？"
> "哦对，不要编造，所有信息都是知识库的对吧？对。"

它没有能力核对自己是否真的用了检索数据——**它在表演检查。**

**这条改变了整个项目的设计思路**：可靠性不能靠 prompt 恳求模型自律，只能靠架构保证（强制检索节点、参数校验、工作流硬连线）。这也是这个行业真正的工程难点，不是"写个好提示词"就完事。

---

### v5：把字段"翻译"成人话

**触发问题**：顾客问"有弹力的上衣"，但数据里是"有弹性 / 微弹 / 无弹性"三个词。顾客分不清，行业也没有统一标准。

**做法**：数据层保留专业字段（方便筛选和推理），展示层做翻译：

| 数据值 | 对顾客怎么说 |
|--------|-------------|
| 有弹性 | 弹力很好，久坐不勒、活动自如 |
| 微弹 | 带一点点弹力，穿着舒服，但版型依然挺括 |
| 无弹性 | 不说"无弹性"，改说面料挺括有型、垂感好 |

**设计原则**：**数据层要专业，展示层要人话。** 这两层必须分开，否则要么数据没法用，要么顾客听不懂。

---

### 如果重来，我会怎么开始

1. **提示词里不写"或"**。想要确定行为，就给确定指令。
2. **每个版本都记录一个"失败样本"**。我保留了三件假裙子的名字和价格，它们比任何成功案例都能说明质量边界在哪。
3. **先想清楚"事实从哪来"，再想"怎么说好听"**。顺序反了就是在给幻觉做包装。

## 七、还缺什么才能商用

诚实说，这是 Demo，离真实品牌落地还差：

1. **数据接入**：真实商品库来自品牌 ERP / PIM，需要接口对接与增量同步
2. **量级**：真实品牌 SKU 几万到几十万，需要向量检索 + 图谱查询，而非关键词匹配
3. **多轮状态**：当前每轮相对独立，商用需维护用户偏好上下文
4. **效果度量**：埋点统计曝光 / 点击 / 加购 / 转化率，用数据证明 ROI
5. **合规**：用户数据存储与使用需符合隐私要求
6. **多渠道**：官网、小程序、门店导购工具、直播弹幕，交互形态各不相同

## 八、三个思考题

### Q1：为什么推荐必须来自真实商品表？

大模型的本质是概率生成，不是数据库查询。它永远会用"最像答案"的方式给你一个商品。零售场景里，编造商品 = 客诉 + 信誉损失。所以**事实性内容必须由外部数据源提供，大模型只负责理解和表达**。这也是知识图谱这类技术存在的根本理由——图谱就是那个事实源。

### Q2：哪些环节适合 Agent 自由发挥，哪些必须固定流程？

判断标准是**结果的确定性要求**：

- 商品检索 / 库存 / 价格 —— 必须固定、可审计、毫秒响应 → 结构化查询
- 意图理解 / 推荐话术 / 多轮追问 —— 输入不可预测，需要灵活 → 大模型
- 合规红线（不许编造、不许承诺折扣）—— 前置规则校验，不能让模型自己决定

一句话：**Agent 负责"想"，工作流负责"稳"，Skill 负责"做"。**

### Q3：这个 Demo 卖给真实品牌还缺什么？

见第七节。核心是数据接入、量级支撑、效果埋点。不是功能不够，而是从"能演示"到"能扛业务"之间需要工程化投入。
